# Agent Loop（智能体执行循环）：AI 是如何一步步完成任务的？

[[toc]]

当我们使用 AI 编程工具时，可能会遇到这样的场景：告诉 AI“帮我修复这个项目的登录问题”，它并没有直接给出一段代码就结束，而是先读取项目文件，分析代码逻辑，修改相关文件，运行测试，发现错误后继续修复，直到问题得到解决。

这背后有一个非常重要的机制：`Agent Loop（智能体执行循环）`。

如果说大语言模型（LLM）是 AI 的“大脑”，负责理解问题、分析信息并决定下一步做什么，那么 `Agent Loop` 就是让这个大脑能够持续行动、接收反馈并调整方案的工作机制。

理解 `Agent Loop`，就能明白为什么普通的 AI 聊天通常是“一问一答”，而 AI Agent 却能够执行一连串操作，逐步完成复杂任务。


## 一、什么是 Agent Loop？

`Agent Loop`，中文通常称为“智能体执行循环”，指的是 `AI Agent` 在执行任务时，反复进行思考、调用工具、获取结果、根据反馈决定下一步行动的过程。

它不是某种特殊的模型，而是一种围绕大语言模型构建的任务执行机制。

普通的 AI 聊天通常是这样的：

```
用户提出问题

“帮我分析一下这段代码”

大模型生成回答

分析代码并返回文本

本轮对话结束
```
而 AI Agent 的工作方式更像一个不断推进任务的执行流程

```text
1. 理解任务:明确目标与当前状态

2. 模型决定下一步:继续分析，或请求调用工具

3. 执行工具:读取文件、运行命令、查询数据等

4. 获取执行结果:成功结果、错误日志或其他反馈

5. 判断是否完成

```
未完成则继续循环，完成则返回结果

未完成时，执行结果会再次进入模型上下文，触发下一轮决策。

两者最大的区别在于：普通聊天主要关注生成回答，而 `Agent Loop` 让模型可以在多轮执行中持续利用外部工具，并根据真实执行结果调整行动。

需要注意的是，循环本身并不意味着模型一定能自主完成任务。它能否成功，还取决于模型能力、工具质量、上下文信息、权限控制以及终止条件。

## 二、Agent Loop 是如何运转的？

继续以 AI 修复登录问题为例，看看一次完整的执行循环是怎样发生的。

### 2.1 第一步：接收任务，理解目标

用户提出需求：

> 帮我检查项目的登录功能，如果有问题就修复，并运行测试。

`Agent` 首先会把用户需求、系统提示词、已有对话以及必要的项目上下文发送给大模型。

模型需要判断当前任务应该怎么推进。例如，它可能决定先查看项目目录，再找到登录相关代码，而不是直接修改文件。

这里有一个关键点：大模型通常负责决定下一步行动，但并不天然拥有读取本地项目的能力。

真正执行读取操作的是 `Agent` 运行环境提供的文件工具。模型需要通过工具调用请求，让运行环境执行对应操作。

### 2.2 第二步：调用工具，获取真实信息

假设 `Agent` 提供了一个 `readFile` 工具，模型可以请求读取登录模块：

```
{
  "name": "readFile",
  "arguments": {
    "path": "src/auth/login.ts"
  }
}
```

上面的内容表示一次工具调用请求，并不是模型直接打开了电脑上的文件。

接下来，`Agent Runtime` 通常会完成以下工作：

1. 检查工具是否存在。
2. 校验参数是否合法。
3. 根据权限规则判断是否允许读取。
4. 调用真正的文件读取函数。
5. 将读取结果返回给模型。

假设工具返回了登录代码，模型就可以根据实际内容继续分析，而不是仅凭猜测生成修复方案。

工具的定义、参数校验与执行过程可以参考 `LangChain` 的工具调用文档。


### 2.3 第三步：根据反馈，决定下一步

拿到登录代码后，模型可能发现一个问题：登录请求失败时，没有正确处理异常。

它可以继续请求调用文件修改工具，修改对应代码，然后请求运行测试的工具。

如果测试返回：

```
FAIL src/auth/login.test.ts

Expected: 401
Received: 500
```

这条错误信息就成为下一轮模型调用的输入。

模型可以据此判断：第一次修改仍然存在问题，需要继续查看错误处理逻辑，或者调整测试相关代码。

于是，执行流程再次进入循环：

```text
模型分析当前信息
        │
        ▼
请求调用工具
读取文件、修改代码或运行测试
        │
        ▼
工具实际执行并返回结果
        │
        ▼
模型根据结果重新判断
        │
        ├── 任务未完成 ──▶ 继续调用模型，进入下一轮循环
        │
        ▼
   任务完成
返回最终结果
```

这就是 `Agent Loop `最核心的机制：每次工具执行都会产生新的信息，模型根据这些信息决定下一步行动。

当然，并不是每次循环都必须调用工具。模型也可以判断现有信息已经足够，直接生成最终回答。

## 三、从代码角度理解 Agent Loop

了解运行原理后，我们可以尝试使用 `TypeScript` 实现一个简化版本。

下面的示例不依赖具体的大模型 SDK，而是通过接口抽象模型调用过程，重点展示循环控制逻辑。

### 3.1 定义模型与工具接口

```
type ToolCall = {
  id: string;
  name: string;
  arguments: Record<string, unknown>;
};

type ModelResponse = {
  content?: string;
  toolCalls: ToolCall[];
};

type Message = {
  role: "user" | "assistant" | "tool";
  content: string;
  toolCallId?: string;
};

type Tool = {
  name: string;
  execute: (
    args: Record<string, unknown>
  ) => Promise<string>;
};

type Model = {
  generate: (
    messages: Message[]
  ) => Promise<ModelResponse>;
};
```

这里定义了三个核心对象：

- `Model`：负责调用大模型，获取模型的下一步决策。
- `Tool`：封装真实的工具执行逻辑。
- `Message`：保存用户输入、模型回复和工具执行结果。

模型返回的 `toolCalls` 表示它希望调用哪些工具。具体能否执行，还要由 Agent 自己判断。

### 3.2 实现执行循环

```
async function runAgent(
  model: Model,
  tools: Tool[],
  userInput: string,
  maxSteps = 10
): Promise<string> {
  const messages: Message[] = [
    {
      role: "user",
      content: userInput,
    },
  ];

  const toolMap = new Map(
    tools.map((tool) => [tool.name, tool])
  );

  for (let step = 0; step < maxSteps; step++) {
    // 1. 请求模型决定下一步行动
    const response = await model.generate(messages);

    // 2. 记录模型回复
    messages.push({
      role: "assistant",
      content: response.content ?? "",
    });

    // 3. 没有工具调用，结束循环
    if (response.toolCalls.length === 0) {
      return response.content ?? "任务已结束";
    }

    // 4. 执行模型请求的工具
    for (const call of response.toolCalls) {
      const tool = toolMap.get(call.name);

      if (!tool) {
        messages.push({
          role: "tool",
          toolCallId: call.id,
          content: `工具不存在：${call.name}`,
        });

        continue;
      }

      try {
        const result = await tool.execute(
          call.arguments
        );

        messages.push({
          role: "tool",
          toolCallId: call.id,
          content: result,
        });
      } catch (error) {
        const message =
          error instanceof Error
            ? error.message
            : "未知工具执行错误";

        messages.push({
          role: "tool",
          toolCallId: call.id,
          content: `执行失败：${message}`,
        });
      }
    }
  }

  return "已达到最大执行步数，任务停止。";
}
```

这段代码展示了 Agent Loop 的基本骨架：

1. 调用模型。
2. 检查模型是否请求工具。
3. 执行工具并记录结果。
4. 把结果带入下一轮模型调用。
5. 没有后续工具调用，或者达到最大步数时停止。

注意：这只是用于理解原理的简化示例，不是可直接用于生产环境的完整 Agent。 真实模型接口还需要正确处理工具调用消息、调用 ID、参数 Schema、上下文管理和权限校验。

实际工程中，也可以使用 `LangGraph` 这样的框架组织循环、状态和条件路由。


## 四、为什么 Agent Loop 不会一直运行下去？

如果模型一直要求调用工具，而工具执行后又持续返回错误，Agent 就可能陷入循环。

例如：

```
模型：运行测试
工具：测试失败

模型：修改代码，再运行测试
工具：测试失败

模型：再次修改代码
工具：测试仍然失败
...
```

因此，`Agent Loop` 不仅需要循环机制，还必须设计可靠的停止条件。

常见的控制方式包括：

| 控制机制        | 作用                     |
| ----------- | ---------------------- |
| 最大执行步数      | 限制循环次数，防止无限运行          |
| 超时时间        | 避免任务长时间占用资源            |
| Token 与费用限制 | 控制模型调用成本               |
| 错误次数限制      | 多次失败后暂停或交由人工处理         |
| 完成条件        | 根据测试结果、业务规则等判断任务是否真正完成 |
| 人工审批        | 对删除文件、发布代码等高风险操作进行确认   |

其中，模型说“任务完成”并不一定代表任务真的完成了。

例如，模型可以声称代码已经修复，但实际测试仍然失败。因此，工程实践中应该尽可能使用构建结果、测试结果、业务状态等可验证的信息判断任务是否完成。工具执行错误也应该被妥善处理，而不是直接丢失。


## 五、Agent Loop 与 ReAct 有什么区别？

在学习` Agent Loop` 时，经常会遇到另一个概念：`ReAct`。

两者有关联，但并不是同一个概念。

- `Agent Loop`：描述智能体反复调用模型、执行工具、接收反馈的整体执行机制。
- `ReAct`：一种将推理（Reasoning）与行动（Acting）结合起来的智能体设计模式。

例如，模型在处理问题时，可以根据当前信息决定搜索资料，观察搜索结果，再决定是否继续搜索或给出答案。这类“思考—行动—观察”的模式，是 Agent Loop 的一种常见实现方式。


并非所有 `Agent Loop` 都必须采用 `ReAct`，也不是所有任务都适合让模型自由决定每一个步骤。对于固定流程，使用明确的程序逻辑或状态机，往往更容易控制和测试。

## 六、Agent Loop 在实际开发中有什么价值？

`Agent Loop` 的价值，不只是让 AI 多调用几次模型，而是让 AI 能够根据真实反馈推进任务。

在 AI 编程场景中，它可以形成这样的流程：

```text
读取项目
分析目录结构，定位目标代码
        │
        ▼
修改代码
根据需求生成修改，并写入文件
        │
        ▼
执行验证
运行测试、类型检查或构建命令
        │
        ▼
根据反馈迭代
读取错误日志，继续修复
        │
        └──▶ 未满足完成条件时，回到「执行验证」继续循环
```

这套机制同样可以用于自动化运维、数据分析、知识检索和业务流程处理。

但需要明确：`Agent Loop` 只是让任务能够持续执行的基础机制。真正可靠的 `AI Agent`，还需要工具系统、状态管理、权限控制、错误处理和结果验证等配套能力。

## 七、总结

理解 `Agent Loop`，可以记住一句话：

大模型负责决定下一步做什么，工具负责真正执行，执行结果再反馈给大模型，由此形成持续推进任务的循环。

当我们看到 AI 自动读取文件、修改代码、运行测试并修复错误时，背后通常并不是模型一次性完成了所有工作，而是运行环境持续协调模型与工具，直到满足停止条件。

这也是 `AI Agent` 与普通问答应用的重要区别：它不仅能够生成内容，还可以在工具和反馈的支持下，一步步推进真实任务。
